# サムネイル作成

版 3.4 / 2026-10-02。ラフ・支給素材・修正履歴を制作条件へ変換し、参考選択 → 背景自動選択 → モデル選択 → 初回3案／修正2案 → 各案検査まで実行する。異なる文字ブロックの接触を禁止し、人物写真の直接配置指定を優先する。

## 必須の提出ルール

- **最初の画像提出は必ず独立した完成画像3案（A・B・C）。修正依頼への提出は毎回2案（R1・R2）。** 1案だけ、文章だけ、3案を1枚に並べた画像では完了しない。各案を同等に仕上げる。ユーザーの後続の明示的な案数指定だけがこの規則を上書きでき、都合や推測で減らさない。
- 生成ツール1回の `output.count: 1` は維持する。**1枚ずつ3回／2回**と、提出案数を別管理する。内部QCの修正回数は提出案数とは別。
- ラフの文言・要素の役割・相対配置と支給素材は全案共通の固定条件。案の違いは許された書体処理・視線の優先順位・新規背景などから選び、固定条件を破って差を作らない。修正2案は両方に全修正を反映する。
- 基準はユーザーが選んだ画像。案を出した順やファイルの新しさで採用画像を決めない。採用前に `final.jpg` を特定案へ自動更新しない。
- 「一発目」は、資料確認・設計・内部検査を済ませた最初の提出。生成を1回しか試せない意味ではない。完全再現やCTRを保証せず、未解決の誤字・偽ロゴ・指定外変更を合格扱いしない。

## 最初にすること

依頼を「チャンネル登録・分析」「サムネ制作」「修正・仕上げ」「収集更新」のどれかに振り分ける。登録・分析だけの依頼に画像生成は不要。制作依頼はプロンプトだけで終わらず、完成画像まで進める。

スキル自身の場所を `SKILL_ROOT`、利用者が指定するかスキル用に設定した作業領域を `DATA_ROOT` とする。実際の絶対パスを解決して使い、文字列の変数名をそのままツールに渡さない。保存先指定があれば優先する。特定のユーザー名・クラウドドライブ・個人環境のパスを仮定しない。

- 画像生成はCodex内蔵ツールが一般の標準。ユーザーがOpenAI API接続を選び、production-policy.jsonで有効化した環境では [モデル自動選択](references/model-routing.md) に従い、同梱APIアダプターでFlare／Sunburstを実際に切り替える。内蔵ツールへのプロンプトだけでモデルを選べたと報告しない。API接続が未完了なら明記し、無断で別方式へ切り替えない。
- Web閲覧とPython実行はチャンネル登録に必要。名前検索はチャンネルURLがない時だけ使う。Python 3.10以降、依存は `requirements.txt`。依存がなければスキル直下に `python3 -m venv .venv` で専用環境を作り、その環境のPythonで `-m pip install -r requirements.txt` を実行する。以後の補助スクリプトもそのPythonで実行する。ツールの有無を実行環境で確認する。
- 画像生成が使えなくても収集と分析は実行できる。制作まで依頼されている場合は未完了部分を明記し、勝手に別サービスへ切り替えない。
- スキル本体にチャンネル画像、ユーザー素材、修正履歴を書き込まない。作業データは `DATA_ROOT` に分離する。
- 優先順位は、今回の明示指示 → 当該案件の承認済み仕様 → 当該チャンネルの承認済みルール → 当該チャンネルの観察 → 共通品質基準。
- `DATA_ROOT/reference-library.json` と `production-policy.json` があれば読む。登録資料の優先チャンネル・全件確認・案件限定の修正条件はこの設定に従う。[横断ライブラリと全件レビュー](references/reference-library.md) はローカル資料の追加、複数チャンネルの学習、登録済みライブラリからの制作時に必須。
- `DATA_ROOT/background-library.json` があれば、制作・修正で必ず [背景の自動選択](references/background-selection.md) を実行する。ラフから条件を言語化し、候補を原寸で開き、背景をAI側で選ぶ。ユーザーに素材番号を選ばせることを既定にしない。背景素材の一覧と過去サムネの全件レビューは別管理。
- 特定チャンネルの色・密度・装飾・ロゴ寸法を別チャンネルへ自動適用しない。任意のビジュアルプリセットは [flashy-ai-tool-preset.md](references/flashy-ai-tool-preset.md)。

## 全案件共通の生成前確認と寸法

[全体FBの固定ルール](references/global-feedback.md) を制作・修正のたびに適用する。スラッシュ囲みは常に左詰め。生成前に既存FBと専用人物写真の有無を確認し記録する。納品は3840×2160で実寸検査し、拡大書き出しはネイティブ4Kと区別する。

**文字とロゴ・人物の軽い重なりは許容するが、異なる文・行・数値の文字同士の重なりは絶対に禁止。** フチ・強い影を含めて余白を確保し、衝突する文字はサイズを下げるか、ロゴに重ねてでも移動する。人物の元写真を直接配置する指定がある場合は、生成で顔を描き直さない。

## チャンネルURLから登録する

[チャンネル収集と分析](references/channel-onboarding.md) を読む。

1. 標準入力はユーザーが渡すYouTubeチャンネルURL。指定URLを開き、正式名・ハンドル・UCで始まるチャンネルIDを取得する。URLで対象が一意ならチャンネル名を聞き直さず、登録・全件収集・分析へ進める。`/@ハンドル`、`/channel/UC...`、旧形式の`/c/...`・`/user/...`、末尾に`/videos`・`/shorts`・`/streams`があるURLに対応する。初回収集は指定URLのタブだけに限定せず、明示された対象範囲に従う。名前しか渡されなかった場合だけ検索し、同名候補が残る時に対象を確認する。
2. `collect_channel.py` をチャンネルIDで実行する。対象範囲の指定がなければ初回は件数上限なしで videos / shorts / streams を対象に、公開一覧をページ送りしながら列挙する。動画本体・音声は取得しない。
3. 実行中は進捗を伝える。中断・警告・未取得は `collection_report.json` で扱い、途中の結果を全件と呼ばない。再実行ではIDで重複を除き、取得済み画像を検証して再利用する。
4. `prepare_analysis.py` で検索可能な全画像ギャラリー、全画像のページ別一覧、分析候補、動画CSVを作る。資料用一覧は画像生成ツールを使わず、保存した参考画像を並べる。生成する完成サムネは1枚ずつという原則と区別する。
5. 一覧と原寸を目視し、[分析の基準](references/channel-onboarding.md) に従って `observations.csv` を記入。集計後、チャンネル直下に `analysis.md` と `channel-profile.json` を作る。観察と提案を区別し、根拠動画ID・母数・確認日を記す。文字や色の特徴を画像を見ずに推測しない。
6. 保存枚数、種類別の範囲、失敗数、目視した枚数、代表ルール、ギャラリーと保存先を納品する。公開一覧で取得できた範囲の完了と、YouTube内の全投稿の網羅保証は区別する。

対象未確定のまま別チャンネルの大量取得を始めない。対象チャンネルが不明な制作依頼では、既存案件のチャンネルIDから判断し、判断できなければチャンネルを特定する。新規チャンネルで公開動画がなければ、ユーザーの参考画像とブランド指示から「仮プロファイル」を作り、学習済みと呼ばない。

## チャンネルに合わせて制作する

[ラフから3案・修正2案](references/rough-to-delivery.md)、[デザインの判断理由](references/design-reasoning.md)、[制作・修正・QC](references/production.md)、[文字とロゴ](references/text-and-logo.md) を読む。人物素材がある場合は [人物の扱い](references/person-identity.md) も読む。過去指摘の再発防止は [修正の独立固定](references/revision-regressions.md) を使う。

1. 対象チャンネルの `channel-profile.json`、`analysis.md`、`memory/corrections.jsonl`、`memory/success_cases.jsonl` を確認する。初回だけ登録・分析から開始。学習済みチャンネルで毎回全件収集し直さない。ユーザーが更新を求めた時や、現在のスタイルとの食い違いがある時に更新する。
2. ライブラリ登録時は、サムネ作成・修正の依頼ごとに全保存サムネを一覧で目視し、全ページの確認記録を残す。前回の記憶や代表例だけで省略しない。その後、同チャンネル・同じ動画種類・近いシリーズの候補2〜4枚を原寸でも比較する。通常動画にショートの構図を混ぜない。外部チャンネルは構図や情報階層の参考に限り、人物・ロゴ・文章の借用元にしない。
3. ラフを実際に開き、テーマ・確定文言・相対配置・支給素材との対応・変更可能範囲を `brief.md` に整理。ラフ内の「ブラー」「影」等は制作注記として解釈し、印字しない。素材を実際に開いて役割、出典、比率、ハッシュを記録。揃った情報は聞き直さず、解釈を短く伝えて進める。
   背景素材集が登録されていれば `background-brief.json` → 検索 → 候補の原寸比較 → `background-selection.json` の選択記録を作る。指定された実画面・写真・場面を抽象背景で置換しない。背景変更がない修正は検索結果を採用せず、承認済み背景と加工値を保持する。
4. `design-decision.json` に比較候補・選択理由・正確な書体名または未確認・文字配色・フチ・影・ロゴ/人物・背景・参照IDを記録してから、プロファイルの数値と文字階層を `assets/thumbnail-prompt.json` に展開し、完全版JSONを保存する。[構図カタログ](references/layouts.json) は選択肢であり、チャンネル独自構図を優先してよい。行数・ブロック数を固定しない。
5. `assets/thumbnail-batch.json` を案件へ複製し、初回3案／修正2案の意図と各完全版JSONを揃える。`scripts/validate_delivery.py --batch <案件/batch.json> --stage plan` で案数・素材・固定条件を確認後、各案を独立画像として生成・保存する。API使用時は各案の `routing_job` を [自動選択手順](references/model-routing.md) に沿って作り、`image_model_router.py plan` → `run` で実行。人物・ラフ・ロゴ・文字を保持する初稿もSunburstを優先し、自由背景はFlareを選ぶ。単一デザイン内の比較構図は可。中間素材は完成案に数えない。
6. **各案**を原寸・320×180・168×94で目視し、要求IDごとに確認を記録。文字・ロゴ・人物・固定部分を元画像と照合して、合否を個別に判定する。誤りは限定修正する。生成編集は画像生成ツールを使い、ローカル合成は利用環境の許可範囲とユーザー指示に従う。
7. 各案の高解像度原本、3840×2160（4K・16:9）の納品JPEG、縮小プレビュー、完全版JSON、`qc.md` を個別に保存。`scripts/validate_delivery.py --batch <案件/batch.json> --stage delivery` に通してから、A/B/CまたはR1/R2を画像表示し違いを一言添える。推奨案は理由付きで示すが、採用を代行しない。実行制限で不足した場合は揃ったとは報告せず、未完了案を明示する。
   素材集から実際に使った背景は `background_library.py record-use` でチャンネル・案件・案・ハッシュを記録する。候補だけでは使用済みにせず、ユーザーの明示採用だけ `approved` にする。

生成・編集は有効なJSONをプロンプト文字列として渡す。`text_lock`、`text_aspect_lock`、`typography_style_lock`、`change_only`、`preserve_exactly`、`output.count: 1` を毎回含める。JSONの指定は画質や形状を保証する機能ではないため、必ず実画像を検査する。

## 修正・仕上げ・チャンネル別学習

- 直前の完全版JSONを複製し、指示された項目だけを変更。承認済み文言・文字面・太さ・色・フチ・影・字間・座標・素材を固定する。
- 文字の配置と塗り/グラデーション、線の太さと不透明度、ロゴとキャラ、上段の導入と下段の結論を独立した項目で固定する。修正で片方だけ変える場合、もう片方を初期値へ戻さない。正確な過去の修正値・採用画像はデータ側のチャンネル/案件記録から読む。
- 「仕上げ」は最新画像を目視し、輪郭・にじみ・ノイズなど必要な修正に限定した再生成を行う。単なるリサイズだけで仕上げ完了にしない。人物の顔と正式ロゴを再解釈しない。
- 毎回の画像・JSONは連番保存。`final.jpg` を更新する前に旧版の連番画像が残っていることを確認する。元素材は削除・移動・リネームしない。
- 修正を「症状 → 原因 → 対処 → 次回の具体的初期値」へ変換し、対象チャンネルの `memory/corrections.jsonl` と案件の `反省.md` へ追記。継続指定だけ `channel-profile.json` に反映。変更前プロファイルを `profile_history/` へ保存する。
- `scope` は `project` / `series` / `channel` を明示。今回限りの指定を全チャンネルの初期値にしない。共通品質上の発見は別途レビュー候補として記録する。
- 成功事例はユーザーが「採用」「OK」「これで納品」と明示した画像だけ。同チャンネルの承認済み例を次回の優先参考にする。

## チームへの引き継ぎ

スキルの共有とチャンネル資料の共有を分ける。スキルには個人パス、認証情報、実案件の顔写真、第三者サムネの実画像を入れない。チャンネル学習を渡す時は、ユーザーが指定した当該チャンネルの `channel-profile.json`・`analysis.md`・根拠IDを基本にする。元画像も共有する依頼がある場合だけ指定範囲を同梱し、相対パスを維持する。メール・チャットへ送信するのは明示依頼がある時だけ。
