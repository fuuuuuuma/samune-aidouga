# 制作・修正・仕上げ・QC

## チャンネルから初稿へ

`channel-profile.json` は、今回に関係する動画種類・シリーズのルールを選んで使う。全期間平均で現在の方向性を薄めない。確定文言、主役語、利用可能素材、根拠参考IDをbrief.mdへ書く。

配置を決める前に実画像を目視する。優先は当該案件の承認済み画像、同チャンネルの採用例、同チャンネルの近い参考、外部の抽象的構図の順。写真中心の料理・旅行・Vlog、文字の少ないゲーム実況、白背景の商品レビュー等に、AIツール型の巨大ロゴ・王冠・派手な帯を自動で持ち込まない。

内部設計をcanvasと各要素のx/y/w/hへ落とす。通常動画の制作・納品基準は3840×2160（4K・16:9）。旧1280座標を再利用する場合は全要素を3倍へ換算する。右下のタイムコード想定領域x=3120..3840、y=1830..2160へ重要情報を置かない。実表示の固定保証ではなく、余裕を持たせるための制作基準。顔の周辺と主役語の可読性を先に確保する。

構図カタログは左右配置・中央配置などの骨格。文字の行数、字高、ブロック数はコピーとチャンネル次第。意図的な余白、単色背景、文字なしのサムネも許容する。特定のビジュアル型との違いを欠点にしない。

## 完全版JSON

assets/thumbnail-prompt.jsonは入力の型。実画像を見て具体値に置換し、不要な文字は `text_lock: []`、`typography.render_text: false` とする。空のテンプレートをそのまま生成に投入しない。

- `channel_context`: チャンネルID、参照プロファイル、シリーズ、参考ID。
- `references`: 画像ごとの役割と、参照しない要素。人物の顔・文字・ブランド等を別チャンネルから引き継がない。
- `text_lock`: 文言を逐語・ブロック別に固定。動画タイトル全体を自動転載しない。
- `layout`: キャンバス・主役・文字・ロゴなどの座標。
- `typography_style_lock`: 字形、太さ、色、グラデーション、フチ、影、帯、字間、座標、サイズ比。承認後はimmutableをtrueへ。
- `text_aspect_lock`: 字形基準と等比拡大。幅合わせの横伸ばし・縦つぶし禁止。
- `change_only` / `preserve_exactly`: 修正対象と保持対象を完全記載。
- `output`: 1枚・単独画像。JSONスキーマを画像モデルが実装していると仮定しない。

ローカル画像は先にview_image等で確認して、実行環境の画像生成ツールの添付仕様に従って渡す。パスを文章に書いただけで画像参照されたと思わない。生成結果の実ファイルを案件フォルダへコピーし、ツールの一時保存先だけに残さない。

モデルを自動で使い分ける環境では [model-routing.md](model-routing.md) を先に読み、ラフ・本人・正式ロゴ・文字・変更禁止部分の保持条件で選択する。OpenAI APIの実行結果は各案の `model_receipt` に紐付ける。プロンプトだけの希望モデルと、APIのmodel引数に指定したモデルを区別する。モデル選択が適切でも、以下の実画像QCは省略しない。

## 文字・人物・ロゴの修正

画像編集は利用環境の画像生成・編集ツールを優先する。限定編集が1回失敗したら同じ曖昧な指示を繰り返さず、対象と保持範囲を整理する。実行環境で許可される場合は、ユーザー提供の実素材・フォントによる後合成を使える。

同梱の `render_thumbnail_composite.py` は任意の補助ツール。Python編集が許可されない環境では使わない。使う時は旧文字・旧影を消した背景またはレイヤー別素材を準備してから描画し、旧文字の上に別文字を重ねて隠すだけにしない。フォントは利用者環境の日本語対応書体を指定する。書体ファイルは配布していない。

```bash
python3 SKILL_ROOT/scripts/render_thumbnail_composite.py --write-example composite_spec.json
python3 SKILL_ROOT/scripts/render_thumbnail_composite.py \
  --spec composite_spec.json --output final.jpg --preview mobile_preview.jpg
```

`layers` 内の文字レイヤーへ `font_path` を実在するフォントファイルの絶対パスで設定するか、`SUMNESSY_FONT` を指定する。Mac以外で自動検出できない場合も、英字専用の代替書体で日本語を描いて完成扱いにしない。各素材のpathはcomposite_spec.jsonを基準にした相対パスにできる。人物は `role: person`、`identity_mode: original_pixels`、`fit: contain`。

後合成レンダラーの標準キャンバスは1280×720。特殊比率・4K制作にそのまま流用せず、画像生成ツールの出力または対応した編集手段を用いる。

## 仕上げ

承認済み画像とその完全版JSONから開始する。輪郭・文字のにじみ・フチの不均一・背景ノイズを点検し、必要な箇所だけ再生成で整える。構図、コピー、色、本人、正式ロゴは固定。参照画像の指定を省かない。直前の崩れた生成ロゴを「公式比率」の基準にしない。

日本語が再度崩れたら限定修正または許可された実フォント補正へ切り替える。補正できなければ、失敗箇所と利用可能な版を示し、完成したと報告しない。人物の再編集は2回までとし、その後は元写真を保つ構成または別の実写真へ戻す。

## QC：全案を個別に合否判定する

初回3案／修正2案を、原寸、320×180、168×94で実際に表示する。大きく表示された画像を頭の中で縮小したつもりにしない。通常動画以外は比率を保った相当サイズを使う。小プレビューは解析用の派生画像であり、生成原本を変更しない。目視の記録は各案の `qc.md` とbatchの `qc_checks` に残す。

| 必須QC ID | 原寸で確認 | 縮小で確認 |
|---|---|---|
| text | 全文をtext_lockと照合。数字・単位・記号・濁点・改行。OCRは補助のみ | 主役語と結果が読める。単位が別の数字に属して見えない |
| layout | ラフの相対位置、各枠の役割、比較方向、全高指定と端切れ | 対象と得られる内容、最初と次に読む要素が分かる |
| assets | 支給ロゴの内部輪郭・元比率・配色。人物、キャラ、実画面を照合 | 対象が分かる。ただし隠す指定の対象は適切に識別しづらい |
| typography | 字形、文字の内側、フチの順序、影のにじみ、グラデーションを参照と比較 | 補足が主文と競合せず、フチが文字を埋めない |
| preservation | 変更禁止領域を基準画像と交互に表示して比較。新規なら固定条件と比較 | 指定外の配置・色・印象の変化がない |
| hierarchy | 主役、補足、結果の優先順位が設計理由に沿う | 背景の模様や装飾が主役より先に目を引かない |
| finish | 素材境界、手、顔、切り抜き、光源、影、不要文字を検査 | ノイズや黒い塊が意味のまとまりを壊さない |
| format | 納品寸法、比率、容量、実ファイルの表示を確認 | 端の欠け、右下表示との衝突を確認。明示の全高指定は優先 |

さらに **request_contractの全要求ID × 全案** を点検する。statusはpass／fix／unknown、noteに確認した箇所と見え方を書く。該当素材がない項目もその理由を記す。固定事項の誤りを、他項目の高評価で相殺しない。旧版の総合95点判定は使わない。

修正では元画像との見比べが必須。数値差分は補助にできるが、生成画像全体の微細な差と実質的なデザイン改変を区別する。「完全に同じピクセル」と主張するなら、対応する領域の比較証拠が必要。強いぼかし・透け感などは元画像と目標の見た目で判定し、レイヤー値を確認していないのに実測と書かない。

提出前に `validate_delivery.py --batch <batch.json> --stage delivery` で記録とファイルを検査する。検査済みファイルのSHA-256を各案に記録し、検査後に画像を変えたら再QCする。スクリプトは案数不足・同一画像の複製・素材の変更・固定プロンプトのずれ・QC漏れを見つける補助で、見た目の合格を自動証明しない。

直せる不具合は提出前に修正。限定修正が失敗したら元画像と指示を再整理し、同じ失敗を漫然と繰り返さない。生成手段の制限で解決できない場合は失敗箇所を隠さず、完成3案／2案を納めたとは報告しない。原稿と素材が揃う通常の制作に、余分な承認段階を挟まない。

1280×720の互換納品を作る場合:

```bash
python3 SKILL_ROOT/scripts/compress_thumbnail.py \
  --input initial/A/original.png --output initial/A/delivery.jpg --max-mb 2
```

圧縮スクリプトは比率が異なる入力を中央クロップする。重要要素が切れる可能性があるため、元画像と出力を確認し、先に構図を合わせる。高解像度の生成原本は残す。拡大処理だけで新しい描写情報が増えたとは言わない。

現在のYouTubeの推奨仕様と、本スキルの互換納品基準は別物。[sources.md](sources.md)参照。ユーザーが4K・Shorts等を指定した場合は比率・寸法と安全域を用途に合わせて設計する。

## 学習ログの最小形式

corrections.jsonlの1行例:

```json
{"date":"2026-09-09","channel_id":"対象ID","project":"案件名","scope":"channel","instruction":"白背景を基本にする","issue":"背景の装飾が多い","cause":"別ジャンルの表現を転用","fix":"白背景と商品写真中心へ変更","next_default":"背景は白、装飾はラベル1つまで","evidence":"案件の承認メッセージまたは画像パス"}
```

継続指示がなければscopeはproject。シリーズ限定ならseries名も記す。チャンネルルールへ反映する時は根拠と日付をプロファイルに追加し、前版を保存する。承認済み成功例は画像・JSONへの相対パス、採用理由、承認日をsuccess_cases.jsonlへ保存する。


生成前と納品時は [global-feedback.md](global-feedback.md) の写真・FB・左詰め・4K検査を必須とする。生成原本の寸法と納品寸法を別々に記録し、拡大出力をネイティブ4Kと報告しない。
