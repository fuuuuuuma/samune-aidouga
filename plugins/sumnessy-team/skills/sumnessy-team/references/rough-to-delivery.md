# ラフ・支給素材から初回3案、修正2案へ

## 1. ラフを制作条件にする

まずラフと支給素材を実際に表示する。撮影された紙の台形、周囲の机、手書き線の揺れは通常は構図指定ではない。紙の中の完成領域を基準に、相対位置を0〜1で読む。ラフの画面比率と納品比率が違う場合は、文字の優先順位と要素間の関係を保って収める。

`brief.md` に次を記す。読める文字をユーザーに再入力させない。どうしても確定できない文言・対象素材だけ、必要最小限の質問にまとめる。その間も素材確認と参考選定を進める。

| 記録 | 例と判断 |
|---|---|
| 動画の約束 | 何の動画で、見ると何が分かるのか。原稿にない実績や効果を足さない |
| 表示文字 | ブロックごとに全文、記号、数字、単位、縦横、改行を区別 |
| 制作注記 | 「ブラー」「人物」「影」や配置矢印は注記。表示文字に混ぜない |
| 要素の役割 | 主見出し、補足、結果数字、正式ロゴ、人物、キャラ、実画面、背景 |
| 固定関係 | 左上にロゴA、左下にB、右にC等。比較方向・重なり・読順も記す |
| 素材対応 | 支給ファイルIDとラフの枠を1対1で結ぶ。ロゴの名前だけで推測しない |
| 許された変化 | 未指定の余白・影の強さ等。座標まで指定された項目を変化軸にしない |

不足資料がなく生成依頼も明示されていれば、設計の承認待ちを挟まない。生成前に解釈と3案の狙いを短く伝える。ラフが未提供でもユーザーが構図を任せた依頼なら進められる。

## 2. 素材と文字を固定する

`assets/thumbnail-batch.json` と `assets/request-contract.json` を案件へ複製する。すべてのパスはそのJSONの場所から解決する。空欄を埋め、説明用サンプルを消す。

素材はID、実パス、SHA-256、役割を記録し、寸法・元比率・透過の有無・出典・許可された加工はbriefに追記する。実人物と架空キャラ、ロゴ本体とタイル・影は別の要素。支給された正式ロゴを第一候補にし、加工された過去サムネを公式原図の代わりにしない。ロゴの変形や人物の追加を案の違いに使わない。

`request_contract.json` に全案共通の `text_lock`、`locked_values`、`requirements` を保存する。`locked_values` は完全版プロンプト内のJSON Pointerと期待値の対応表。例：`/typography_style_lock/fills_and_gradients`、`/layout/elements/2/opacity`。決まっている項目は具体値で固定し、曖昧な「そのまま」だけにしない。未指定の見た目を無理に数値化して事実扱いしない。

ラフ・支給素材・修正指示は要求ID（例R01）に対応させ、全案へ漏れなく適用する。文字の内容とスタイルは別管理する。「1hを赤く」は文言を変えない。素材IDは各プロンプトの `asset_ids` と実際の画像添付に対応させる。**JSON中のパスを書くだけでは画像添付にならない。**

## 3. 全件を見る → 候補を比較する → 判断を残す

[横断ライブラリ](reference-library.md)に従い、同じユーザー依頼につき登録全画像を一巡する。同じ依頼のA/B/Cや内部修正で、同じ全件確認を三重に行う必要はない。別の修正依頼では再度一巡する。

対象チャンネルの承認済み参考を基準に、動画の用途が近い2〜4枚を原寸で比較。必要なPSDの書体・効果・親グループも読む。他チャンネルは参考の引き出しとして使い、そちらの顔やコピーを入れない。

`design-decision.json` は各案に対して「観察した特徴 → 見え方の理由 → 今回の目的 → 具体的処理 → 縮小時の検査」を記す。フォント名はPSD実測／視覚上の候補／使用予定を区別する。生成画像へフォント名を書いたことを、その書体が正確に適用された証拠にしない。

## 4. 初回は完成画像3案

3案はすべてラフ・コピー・支給素材・必須配色を守る。その上で許される範囲の異なる仮説を立てる。次の型は例であり、毎回同じ差に固定しない。

| 案 | 仮説例 | 動かしてよい項目の例 |
|---|---|---|
| A | 近い主チャンネル採用例の情報順が今回にも合う | 近いPSDの書体・フチ・影を役割別に適用 |
| B | 最重要語と結果をより早く見つけられる | 未固定の字高比、間隔、文字裏の静かな領域 |
| C | 主役と背景の奥行き分離が内容を助ける | 未固定の背景の光源位置・ボケ・奥行き、補助物の密度 |

金属グラデーションを必須指定された時にBだけ単色にしたり、縦配置の指示をCだけ横配置にしない。「派手・地味・適当」の3段階や、1枚を複製した偽の3案は禁止。色だけ変える比較が目的なら色違いも可。差別化できる箇所がない場合は、固定条件を守った独立生成3案として仕上がりを比較し、その旨を書く。

## 5. 修正は完成画像2案

ユーザーが指した画像・採用画像を両案の共通ベースにする。修正途中の失敗画像を次々と再編集して劣化を重ねず、同じ基準画像と累積の修正条件から派生させる。ベース画像・プロンプトのハッシュをbatchへ保存する。

両案とも全修正を反映し、違いは許された修正幅の中だけに置く。「65%」が明確なら両案65%を狙い、80%版を比較案として混ぜない。「もう少し大きく」なら控えめ／やや強めの2案にできるが、変更禁止のフチ・グラデーション・背景を動かさない。完全指定なら同じ条件の独立した2生成を検査し、無理な違いを発明しない。

`revision.allowed_change_paths` はプロンプト内の変更可能な末端項目を列挙する。`/layout` 全体など広すぎる許可にせず、ユーザーの指示と対応させる。比較する設計項目の指定外変更は検査スクリプトでも弾く。実画像の一致は別途目視する。

## 6. 出す前の確認と納品

各案を[制作・QC](production.md)で検査。案数、異なる画像ファイル、素材ハッシュ、逐語コピー、固定値、確認記録を次で検査する。

```bash
python3 SKILL_ROOT/scripts/validate_delivery.py --batch 案件/batch.json --stage plan
python3 SKILL_ROOT/scripts/validate_delivery.py --batch 案件/batch.json --stage delivery
```

検査は画像の美しさや字形を自動判定しない。目視していないQCを先にpassにしない。どの案も未解決項目なしにしてからA/B/C、R1/R2として個別表示し、差と推奨理由を一言添える。未採用画像も残す。ユーザーの採用後だけ、その画像をfinalと成功例に記録する。

ユーザーが後で「今回は1案だけ」等と明示した場合は `count_override` に案数と発言の根拠を記録する。例外を自作して3案／2案を回避しない。URL登録・分析・スキル改善だけの依頼は案数規則の対象外。

## JSON記録の具体例

contractのassets要素は `{"id":"claude_logo","path":"assets/claude.png","sha256":"実ファイルのSHA-256","role":"official_logo"}`。requirements要素は `{"id":"R01","instruction":"支給Claudeロゴのオレンジ地と白マークを保つ","basis":"今回の指示と支給ファイル"}`。空のテンプレートを完成条件として使わない。

revisionではvariantsを2件へ変更し、phaseをrevision、各promptのbatch_contextも同じrequest_id・phaseと自身のvariant_idへ更新する。revision欄には `image`、`image_sha256`、`prompt`、`prompt_sha256`、`allowed_change_paths` を保存する。例：`["/layout/elements/0/opacity"]`。文字色変更などは、その案件の実際のJSON構造に対応する末端パスを使う。

delivery時には各案の `image_sha256`、ISO形式の `checked_at`、実ファイル `qc_file` を記入。`qc_checks` はproduction.mdの8項目と全要求IDについて `{"status":"pass","note":"実画像で何を確認したか"}` を記録する。単なる自己申告で合格を作らず、確認後に記す。
